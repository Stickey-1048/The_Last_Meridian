## Inventory and save/load feasibility

Owned SDK `ObjectReference.psc` declares `RemoveItem(Form,int,bool,ObjectReference)` and `AddItem(Form,int,bool)` with **no returned success value or request identifier**. Item-added/removed events identify form/count/reference/source or destination, not the contract's nonce. Therefore no honest design can infer universal exactly-once execution across an arbitrary native-call/save boundary from later inventory counts alone.

The contract's conservative finite policy makes this implementable without a new transaction framework:

- Before the first effect, persist kind, monotonic request number, exact actor/control/item identity, quantities, current step, baseline counts and phase. Revalidate the live actor, actual control reach/context, inventory, stock and exact menu return0 immediately before issuing the effect. Reject donations that would exceed the checked accounting cap **before** taking food.
- Persist `removalAsked`/`deliveryAsked` before each native call. Each irreversible call is issued at most once for that request. Cancellation/stale context before any effect closes without debit; do not claim an effect from selecting a menu.
- Purchase is a two-phase debit then delivery:20actual caps removed/acknowledged, then one10Corn delivery/acknowledgment. It consumes shop stock once, never directly adds reserve. An uncertain debit must not cause delivery; uncertain delivery must not cause a second AddItem. A real acknowledged transfer is not rolled back merely to make later dialogue convenient.
- Bound the immediate acknowledgment window to the active request. A dedicated noninteractive receipt container can corroborate a donation's source/destination counts if explicitly supported, but is optional bookkeeping, not a new service or proof of a native transaction ID. It must not become withdrawable/resellable stock. Ordinary item events alone do not supply a nonce.
- On load, timeout or uncertain continuation, preserve and block the operation; do not infer success from a later unrelated count change, issue automatic retries/refunds, or let another operation reuse its identity. Existing native latent-stack resumption needs an actual healthy-load gate. The allowed blocked diagnostic state is a real limitation, not guaranteed recovery or a successfully completed transfer. If root needs seamless repair of every ambiguous request, that is a larger requirement than this API currently proves.

This is sufficient for normal acknowledged repeatable donation/purchase flows and fail-closed adverse paths. It is not a claim that inventory callbacks or save behavior already ran. Native tests must cover actual debit/delivery and one ordinary reload before handing it to the owner.
